1. 当前整体进展

围绕“Event → TTT → Execution → RoundReview → TTT”的链路，已经把核心流程接通，并开始在开源数据集上做反复验证。

已经完成的部分

  • Planner、Executor、Reviewer 三角色职责已经拆分清楚。
  • TTT 溯源任务树、执行记录、轮次复盘均已结构化落库。
  • Web 首页和 war room 已经能展示真实运行状态，而不是假数据页面。
  • 支持多轮推进，能够观察事件从待处理到完成的全过程。

当前调优重点

  • 在 BOTS 数据集上测试不同告警输入下的任务拆解质量。
  • 优化 Executor 的工具路由与 Splunk 查询意图翻译。
  • 观察每轮复盘是否能有效收敛问题并驱动下一轮调查。

一句话概括当前阶段：整体 workflow 已经打通，接下来主要工作不是“再搭框架”，而是“持续在真实数据集上跑、看效果、改细节”。

Dataset

2. BOTS 数据集介绍

BOTS（Boss of the SOC）是 Splunk 提供的开源安全分析数据集，适合用于攻击溯源、日志关联分析和查询策略验证。

为什么选它

  • 数据公开，便于复现实验与阶段性展示。
  • 包含主机、网络、边界设备等多类型日志。
  • 适合模拟真实 SOC 调查中的证据链拼接过程。
  • 有利于验证多轮调查 workflow 是否可泛化。

当前项目中的使用方式

  • 默认使用 `botsv1`，同时预留 `botsv2` 和 `botsv3`。
  • 通过 Splunk REST API 执行真实检索，不是离线 mock。
  • 重点验证 TTT 任务拆解与日志查询是否能对应起来。
  • 持续观察查询摘要、样本事件与复盘结果是否合理。

典型日志类型

  • Windows / Sysmon
  • IIS / HTTP / DNS / Stream
  • Suricata / FortiGate
  • 注册表与主机行为日志

对当前阶段的价值

  • 能把“多智能体流程”落到实际日志调查场景中。
  • 便于比较不同查询策略和任务树设计的优劣。
  • 为后续接入更多安全工具提供统一验证基线。

Tech Stack

3. 前后端技术栈

当前实现以“轻量、可运行、便于快速迭代”为原则，优先保证链路真实可验证，而不是过早追求复杂部署。

后端

  • Python 3.13
  • Flask + Flask-SocketIO
  • SQLite 作为共享状态中心
  • OpenAI 兼容接口封装 LLM 调用
  • Splunk、VirusTotal、IPInfo 工具接入

前端

  • Jinja2 模板页面
  • Bootstrap 5
  • 原生 JavaScript
  • Socket.IO 实时消息推送
  • 首页 + War Room 双页面结构

运行结构

Web 层
↓
Planner / Executor / Reviewer
↓
SQLite + TTT + Execution + Review
当前技术选型的目标很明确：先保证系统能稳定跑通、能被观察、能被验证，然后再逐步替换为更复杂的调度或存储方案。

Next Step

5. 下一步工作

在当前闭环已经跑通的基础上，后续重点会从“搭框架”转向“提效果、补能力、做验证”。

持续验证与调优

  • 继续在 BOTS 数据集上测试不同类型告警输入。
  • 观察 TTT 任务拆解是否稳定、是否贴合真实调查流程。
  • 优化 Splunk 查询生成质量，减少无效检索和结果偏差。
  • 对多轮复盘过程做分析，提升问题收敛效率。

能力补全

  • 继续丰富可调用的安全工具，增强证据获取能力。
  • 完善前端展示，让 TTT、执行记录和复盘结果更直观。
  • 补充更多标准化测试，提升系统稳定性和可复现性。
  • 为后续替换更强的调度与存储方案打基础。
下一阶段目标可以概括为三点：第一，让 workflow 在更多真实数据场景下跑稳；第二，让查询与复盘结果更准确；第三，让系统从“可运行原型”逐步走向“可持续迭代的研究平台”。
